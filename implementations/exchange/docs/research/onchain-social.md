# Exchange: onchain social reuse research

This is **historical bounded research**, 2026-09-10. It was followed by the original ECP implementation, isolated Shanghai tests, additive deployment144–157 and browser QA159–173. Current exact dependency pins, final reaction semantics and evidence are in [ONCHAIN-SOCIAL.md](../../ONCHAIN-SOCIAL.md). The exploratory statements below describe the research stage, not current readiness.

## Recommendation

Use **Ethereum Comments Protocol (ECP)** for comments/replies/edit/authorship, with one ONCM hook that supplies profile/blog indexing, strict vote semantics, and permanent state-readable revisions. Use **Solady SSTORE2** inside that hook for immutable revision bytes. This reuses a real social protocol, rather than claiming that a storage library by itself supplies a social application.

ECP already provides a Solidity protocol, SDK, React integration and a Ponder indexer. Its repository also has a local Anvil development path. For Exchange, retain the existing React/ethers interface and RPC reads initially: the hosted ECP indexer cannot index our private localhost chain automatically, and importing its whole demo would add unnecessary services. [ECP monorepo](https://github.com/ecp-eth/comments-monorepo/tree/c301d76fa56b6b807f135c98273ac9eb5ddebe95), [integration documentation](https://docs.ethcomments.xyz/).

The alternative with the smallest deployed surface is a purpose-built social contract using Solady SSTORE2 and OpenZeppelin authorization primitives. It saves ECP's manager/library/channel machinery, but requires us to own every posting, revision, reply, identity and voting rule. It is an honest **more custom application** option, not stronger reuse. Prefer ECP unless a bounded compile/size/gas spike shows the integration disproportionate.

## What is actually onchain

ECP's `Comments.Comment` contains `author`, timestamps, `parentId`, `channelId`, and full `string content` / `targetUri`. `CommentOps.createComment` writes content to Solidity state; `getComment` reads the stored struct. It is not merely a hash, calldata or IPFS pointer. Metadata values also live in contract storage. [Types](https://github.com/ecp-eth/comments-monorepo/blob/c301d76fa56b6b807f135c98273ac9eb5ddebe95/packages/protocol/src/types/Comments.sol), [manager/getter](https://github.com/ecp-eth/comments-monorepo/blob/c301d76fa56b6b807f135c98273ac9eb5ddebe95/packages/protocol/src/CommentManager.sol).

An important limit: editing replaces the current content, and deletion clears the stored comment. Full events preserve historical text in receipts, but an application requiring every revision to remain readable from **current chain state** needs more. Its add/edit/delete hook receives the relevant full comment and metadata. At add and every edit, archive `abi.encode(version, author, parent, kind, topic, content, metadata, timestamp)` to an immutable SSTORE2 pointer and append that pointer to the entry's revision list. A deletion is a tombstone; it never erases archived data. This works without modifying ECP core. [Creation/edit/delete and callback order](https://github.com/ecp-eth/comments-monorepo/blob/c301d76fa56b6b807f135c98273ac9eb5ddebe95/packages/protocol/src/libraries/CommentOps.sol).

SSTORE2 stores bytes in deployed runtime code and reads via `EXTCODECOPY`. The chosen implementation prefixes the code with STOP. Respect EIP-170: with its one-byte prefix, one pointer holds at most **24,575 payload bytes** on ordinary EVM; do not copy the older README's 24,576 payload claim without accounting for that prefix. Initial text limits should leave room for encoded revision metadata, e.g. 8 KiB body plus small metadata; larger articles require explicit chunking and paging. No gas estimate has been measured in this research. New immutable revisions cost gas and state even when a user later hides a post. [Reviewed Solady SSTORE2 source](https://github.com/Vectorized/solady/blob/2afba69bf67b78dd4abeadcc696052b3a6f71499/src/utils/SSTORE2.sol), [EIP-170 limit](https://eips.ethereum.org/EIPS/eip-170).

## Product mechanics and required glue

| User action | Reuse | ONCM-specific rule / data |
| --- | --- | --- |
| Save display name / bio | ECP text + metadata + authenticated edit | A profile root owned by its wallet; latest profile entry indexed by address; all revisions archived |
| Publish a personal blog post | ECP top-level text comment and author | Typed blog root and canonical wallet topic; author equals topic wallet; title/body onchain; paged author post IDs |
| Comment on a market or blog | ECP `parentId` / `targetUri`, same-channel reply validation | Canonical market reference includes chain, registry address and statement ID; root exists; topic inheritance cannot change during editing |
| Reply / edit own reply | ECP owner checks and edit nonces | Fixed original author/parent/type/topic; immutable full-content revision pointer per edit |
| Upvote / downvote / remove vote | ECP reaction entries and original atomic delete+post batch | Exactly one current vote per `(entry, wallet)`, values -1/0/+1, reject self-vote; preserve vote event/history. ECP prohibits reaction edits. |
| Read Top / New | Existing React sort, RPC reads or rebuildable index | Current onchain score; stable timestamp + ID tie break; consistent block tag; bounded pagination |
| Inspect history | Original receipt events + hook revision getters | Full revision bytes can be reconstructed without an offchain content server or historical state RPC |

ECP reaction `commentType=1` is only a category: core accepts arbitrary strings and distinct IDs. It does **not** by itself provide one vote per wallet or prevent self-voting. The hook must enforce the allowed reaction alphabet, reference a real non-reaction entry, keep `(target, author) → reactionId/value`, and clear current vote on deletion. Final implementation correction: original `noEditingReactions` rejects reaction edits; sign changes use original atomic delete+post batches with no vendor patch. A user can return to zero or switch sign, but cannot increase weight by posting extra reaction IDs. All paths, including core batch calls, pass the same hook; merely enforcing this in the router or UI would be bypassable. [Reaction model](https://docs.ethcomments.xyz/comment-data-props), [hook interface](https://github.com/ecp-eth/comments-monorepo/blob/c301d76fa56b6b807f135c98273ac9eb5ddebe95/packages/protocol/src/interfaces/IHook.sol).

For the first integration, require direct wallet authorship in the app hook: the actual caller passed by ECP equals the stored author. Calling `postComment` with `author=app=wallet`, empty app signature and the wallet transaction works because ECP recognizes `msgSender == app`. No server credential becomes authorship authority. Signed relaying could be added separately; it is not needed here. SIWE may remain for private local conveniences, but social write endpoints must stop mutating the authoritative JSON database. [Signature implementation](https://github.com/ecp-eth/comments-monorepo/blob/c301d76fa56b6b807f135c98273ac9eb5ddebe95/packages/protocol/src/libraries/CommentSigning.sol).

## Deployment without resetting chain 31372

1. Later, compile a separately pinned social artifact set. ECP uses external Solidity libraries: link `MetadataOps` before `CommentOps`, then include `Approvals`, `Batching` and all compiler-reported link references. Do not assume one manager artifact is self-contained. No compilation happened in this research.
2. Deploy new libraries, unchanged `ChannelManager` and `CommentManager`, and the ONCM hook. Set `CommentManager.updateChannelContract` once during initialization. Existing registry, balances, pools, Governor and proof profiles remain untouched.
3. Set social protocol fees explicitly to zero for this local application. Upstream defaults are **0.02 ETH to create a channel**, zero comment-creation fee and 200 bps on hook ETH revenue. Those are configurable values, not unavoidable charges for every post. No token incentive is proposed. [Fee implementation](https://github.com/ecp-eth/comments-monorepo/blob/c301d76fa56b6b807f135c98273ac9eb5ddebe95/packages/protocol/src/ProtocolFees.sol).
4. Create **one app channel** with the ONCM hook. The upstream channel manager is ERC721. Keep that internal channel token in an immutable holder with no transfer/approval/hook-change interface; users neither mint nor trade profile/blog NFTs. After verified initialization, freeze CommentManager ownership so its manager reference cannot bypass the hook; freeze the channel manager fee owner according to the chosen immutable setup. Retaining any governance ability to replace hooks must be disclosed as a change to social guarantees. [Channel ownership/hook setters](https://github.com/ecp-eth/comments-monorepo/blob/c301d76fa56b6b807f135c98273ac9eb5ddebe95/packages/protocol/src/ChannelManager.sol).
5. Add a new social deployment manifest and observed deployment block; independently bind chain ID, registry and channel in the SDK. The frontend/indexer accepts only this configured channel. Posts on ECP's default or another channel cannot enter ONCM's canonical scores/profiles.
6. Preserve old offchain records as visibly **legacy offchain history**. An operator cannot manufacture wallet transactions to migrate them. Authors can explicitly republish their own records with a wallet transaction. Display both provenance and publication block; never relabel an old JSON record as chain-authored.

## Why not adopt Lens / ENS as the full solution

**Lens V3:** the examined commit `4ad9ab574efc589ac0b90ea103d3aa465bb6368c` uses EVM addresses as profiles and has reusable feed/reply primitives under GPL-3.0-only. `FeedCore` persists a `contentURI`, not a required inline article. A `data:` URI could contain the whole text, so Lens is not fundamentally incapable of full onchain content, but that policy and permanent revision storage would still be our additions. Its deployment/configuration targets zkSync/Lens and explicitly suppresses the classic EVM size warning; plain local EVM compatibility and sizes require a spike. Taking the full Accounts/Rules/AccessControl/Factories stack adds machinery that Exchange does not currently need. It also does not eliminate the required vote/profile/blog semantics. [Lens FeedCore](https://github.com/lens-protocol/lens-v3/blob/4ad9ab574efc589ac0b90ea103d3aa465bb6368c/contracts/core/primitives/feed/FeedCore.sol), [configuration](https://github.com/lens-protocol/lens-v3/blob/4ad9ab574efc589ac0b90ea103d3aa465bb6368c/foundry.toml), [project and license](https://github.com/lens-protocol/lens-v3/tree/4ad9ab574efc589ac0b90ea103d3aa465bb6368c).

**ENS text records:** `TextResolver` really stores arbitrary string values onchain (MIT). It is useful for interoperable profile fields when a user owns an ENS node, but the public resolver authorizes through ENS ownership/delegation. Requiring each local wallet to register a name would introduce an unwanted identity dependency. A wallet-keyed subclass is possible but would be a custom authority adapter, not actual ENS name ownership. Text records do not supply replies, unique votes, a blog feed or immutable revision enumeration, so they do not replace ECP. [ENS text resolver](https://github.com/ensdomains/ens-contracts/blob/5141a2acdf77cf49f5134d674c2792b30f5ee0db/contracts/resolvers/profiles/TextResolver.sol), [public authorization](https://github.com/ensdomains/ens-contracts/blob/5141a2acdf77cf49f5134d674c2792b30f5ee0db/contracts/resolvers/PublicResolver.sol).

## Bounded next validation

Before picking the final build: compile only the selected ECP graph and our minimal hook under a memory/time guard; verify code/link sizes on ordinary EVM. Then isolated tests should cover direct-core versus UI paths, spoofed author, foreign channel, duplicate/self/switched/removed vote, edited metadata rebinding, reply roots, full revision readability after delete, manager/hook immutability, and local RPC pagination. These tests would be separate from a later real browser profile → blog → reply → vote → edit/history pass. No current test or manual success is claimed for this new feature.
