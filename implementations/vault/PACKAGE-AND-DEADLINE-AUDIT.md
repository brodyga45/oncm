## Deadline branches still needing browser coverage

Current manual evidence covers ResolvedAs parent-pending rejection and both eventual sides through188. `scripts/economics.mjs` also tests a future ResolvedBy pending then true after a timely parent proof. It does not replace a browser check of expired false and timestamp equality.

`contracts/Protocol.sol` uses accepted **onchain resolution timestamps**, not discovery time. ResolvedBy(kind1) is True if parent settled at or before deadline; otherwise it becomes False only when current timestamp is strictly greater than deadline. ResolvedAsBy(kind3) becomes False immediately if parent accepted the other outcome, True for the requested timely outcome, or False after expiry. At exact deadline with a pending parent both remain pending. The separate ResolvedWithinWindow operator compares inclusive start/end and only expires strictly after its end.

Concrete manual sequence: derive ResolvedBy from falsebase148 with a deadline later than its recorded resolution → True; use an earlier deadline → False. Create ResolvedAsBy requesting True from that false base → immediate False. For pending/expiry, create an unresolved derivative dependency and a future deadline, confirm pending sends no transaction, then explicitly advance local chain time strictly beyond the deadline and settle False. Test exact equality separately using a controlled next-block timestamp; use the real receipt timestamp as evidence. Do not advance time during someone else's forms or infer any of these unexecuted branches from the passing ResolvedAs cycles.
