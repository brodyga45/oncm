# Vault — основной публичный локальный стенд

Vault V2 доступен по постоянному адресу
[sasquatch-impart-basil.ngrok-free.dev](https://sasquatch-impart-basil.ngrok-free.dev).
Аккаунт ngrok авторизован; перенос управления, начальных средств и будущих комиссий
выполнен в блоках 564–584. Рабочее состояние и транзакции перенесены в компактный checkpoint; финальная проверка запуска описана ниже.
Vault — единственная активно развиваемая реализация; Agora и Exchange сохранены как
замороженные исследовательские варианты. Публичная подписанная EAS-транзакция прошла
в блоке 753; прежний receipt блока 584 доступен после восстановления.

## Требования и выбранная эксплуатация

- Компьютер владельца продолжает обслуживать **существующую** цепочку 31373;
  instance `554c825d-6813-43bf-9bf0-6ede06acff4d`. История до блока563 включительно
  описана в предыдущих browser/economic evidence; сброс и незаметный redeploy запрещены.
- Владелец управления и начальных тестовых средств, явно указанный пользователем:
  `0x4b5d2b35f36a3ac018d5c9a9c394fadae667fb2f`.
  Ключ остаётся только в его кошельке. Членство переносится через Governor/Timelock.
- Пользователь выбрал ngrok. Используется закреплённый dev domain авторизованного
  аккаунта: `https://sasquatch-impart-basil.ngrok-free.dev`. Cloudflare Quick Tunnel
  не используется: его адрес меняется при повторном создании.
- nginx обслуживает production `dist/` и проксирует только `/api/` и `/rpc` на Express.
  Anvil слушает только loopback9547. Публичные клиенты подписывают транзакции в собственном
  EIP-1193 кошельке; сервер не принимает seed/private keys и не подписывает за пользователей.
- `launchd` поддерживает отдельные процессы цепочки, API и nginx и перезапускает упавший
  процесс. Пользовательские LaunchAgents стартуют при входе пользователя в macOS;
  это не обещание доступности выключенного/спящего ноутбука и не root LaunchDaemon до логина.
- Новый сертификат пользователь получает вне сайта. Веб импортирует готовые сертификаты
  и проверяет их через настоящий EVM verifier. Серверное Lean/zk вычисление отключено.
- Для участия нужен тестовый ETH этой локальной цепочки; для LP/торговли — также T.
  На первом этапе владелец раздаёт полученные тестовые средства другим кошелькам.
  Автоматический faucet/relayer не является готовой функцией этого выпуска.

## Границы публичного API

Публичный режим включается только точным HTTPS origin и V2 deployment. Конфигурация
не экспортирует локальные пути, dev аккаунты или recovery metadata. RPC имеет явный
список методов, предел газа/размера/параллельности/частоты. Не публикуются unlocked
`eth_sendTransaction`, node admin/mining/impersonation API. Подписанные транзакции
проверяются на chainId и запрещённые общеизвестные dev senders. Это дополняет,
а не заменяет реальный перенос привилегий и средств с тестовых адресов.

Операции открываются только после onchain readiness проверки. Наличие флага в env
не подтверждает перенос прав. EAS профили, комментарии, голоса и блоги записывает
кошелёк пользователя напрямую в цепь. Серверный индекс можно восстановить из событий.

## Файлы эксплуатации

- `implementations/vault/ops/prepare.py`: генерирует nginx, config и launchd plist
  в ignored `.state/pilot/`; сам не устанавливает и не запускает службы.
- `implementations/vault/ops/service.mjs`: entrypoint отдельной службы;
  никаких deployment/mint/proving при старте.
- `.state/chain/`: рабочий snapshot и резервные копии. Восстановление checkpoint 668
  проверено. Для следующих перезапусков также нужны согласованный валидный snapshot
  и контроль блока/instance после старта.
- `.state/pilot/`: локальные пути, журналы и конфигурация окружения, не публикуются в git.
- SDK/public API подробности: `implementations/vault/docs/public-wallet-ui.md` и
  `implementations/vault/docs/public-api.md`.

## Проверка сохранения и обнаруженные ошибки перезапуска

После штатной остановки старой цепи создан полный архив584:630005357bytes,
SHA256 `c8c92dc56622acc7b99cb479b912a5a5081c7d76a2129add225b5b2b0c4439b3`.
Это фактически скопированный и потоково проверенный `.state/chain/pre-pilot-584.json`,
а не ссылка на предполагаемую копию. Никаких600МБ `JSON.parse` не требуется.

Первый запуск выявил старый дефект: `--timestamp genesisTimestamp` переписывал время
следующих блоков после загрузки snapshot. Пустой блок585 имел тот же stateRoot, что584,
но более раннее время. Публичный API/туннель в тот момент ещё не работали. Кроме того,
прямой `launchctl bootout` прервал запись `.state` и оставил неполный JSON.

Этот неопубликованный запуск отменён восстановлением **проверенного584**, с повторной
проверкой SHA256. Проблемный файл сохранён как `.state/chain/failed-first-restart.json`,
а разбор пустого блока и причина восстановления — в `.state/pilot/`.
Ни одна транзакция переноса владельцу не отменена. Автоматический откат не включён.

Исправления: восстановление времени из snapshot; отдельный файл native dump и атомарно
публикуемый проверенный checkpoint; `manage.py stop` сначала завершает supervisor,
ждёт финальный checkpoint и лишь затем выгружает launchd job. `ProcessType=Standard`
не даёт macOS растягивать чтение большого snapshot фоновым дисковым throttling.
Запись native dump каждые30с означает окно потери непроверенного хвоста при аварии:
30с **плюс** время записи/копирования/проверки, а не гарантию нулевой потери.

Рабочее состояние и транзакции перенесены в компактный checkpoint; финальная проверка запуска описана ниже. Текущий pilot запускается
**без `--preserve-historical-states`**: snapshot занимает примерно 9.9 MiB вместо прежних
450–600 MiB. Это изменение режима сохранения исторических состояний, а не новый genesis
или повторное развёртывание контрактов. Архив 584 выше остаётся свидетельством предыдущего
этапа, его размер не описывает текущий рабочий snapshot.

Компактный snapshot не даёт обещания произвольного `eth_call` по всем прежним блокам.
Доступность старого receipt блока584 подтверждена фактическим чтением через публичный RPC. Для резервного копирования и восстановления используются
проверенные checkpoint-файлы, а не предполагаемое сохранение каждого исторического состояния.

## Подключение и обслуживание

### Первый вход и приглашение друга

Аккаунт участника — его собственный адрес кошелька. Администратор не создаёт ему
логин или пароль. Друг создаёт свой кошелёк, подключает ту же сеть и передаёт только
публичный адрес для получения тестовых средств.

1. Открыть сайт в браузере с кошельком, поддерживающим custom RPC, например MetaMask.
   В текущем UI используется `window.ethereum`, отдельного выбора среди нескольких
   расширений нет. Если подключается Uniswap вместо MetaMask, использовать профиль
   браузера с одним активным кошельком MetaMask и перезагрузить страницу.
2. Нажать «Подключить кошелёк» → «Browser wallet», разрешить подключение аккаунта,
   добавление сети и переключение на chain31373. Если нужно добавить сеть вручную,
   использовать параметры ниже; block explorer URL оставить пустым.
3. Средства и MEMBER владельца находятся на
   `0x4B5D2B35F36a3AC018D5c9a9C394Fadae667Fb2f`. Для управления ими совместимый
   кошелёк должен контролировать именно этот адрес. Создание нового аккаунта в MetaMask
   само по себе не переносит туда прежние средства или права. Секреты импортируются
   только самим пользователем внутри его кошелька, не через сайт или чат.
4. Для выдачи другу средств владелец выбирает именно Vault31373 и через Send в кошельке
   переводит, например,1 тестовый ETH для газа и20 T для торговли. Это две транзакции.
   Нужен ETH именно этой локальной цепочки; ETH Mainnet/Sepolia здесь не используется.
5. Чтобы T появился в списке активов кошелька, добавить пользовательский токен по
   адресу ниже, symbol T, decimals18. На сайте баланс T читается непосредственно из
   контракта; добавление токена в кошелёк только меняет отображение.

Тестовые средства не предоставляют голосовой вес: MEMBER выдаётся отдельно через
Governor. Для обычной торговли, LP, профиля, комментариев и блога MEMBER не нужен.
Автоматического faucet и формы обычного личного перевода ETH/T на сайте пока нет;
личные переводы выполняются кошельком. Панель Treasury относится к средствам казны
и governance, её не следует путать с отправкой личных T другу.

Справка MetaMask: [сети](https://support.metamask.io/configure/networks/how-to-add-a-custom-network-rpc),
[отображение токенов](https://support.metamask.io/manage-crypto/tokens/how-to-display-tokens-in-metamask/),
[отправка](https://support.metamask.io/manage-crypto/move-crypto/send/how-to-send-tokens-from-your-metamask-wallet).

## Исправление идентичности genesis при повторном запуске

После компактного checkpoint 772 строгий readiness снова закрыл запись: восстановленный
Anvil отдавал один из дополнительных пустых genesis-заголовков с timestamp восстановления.
Это отдельная ошибка первоначального `--timestamp=resume` подхода; проверку identity
не ослабляли. В snapshot находились исходный genesis и три дополнительных блока с номером0.

Узел штатно остановлен на840. `scripts/repair-pilot-genesis.mjs --apply` сохранил отдельную
копию, проверил RLP/Keccak исходного genesis по parentHash неизменённого блока1 и удалил
только три дополнительных пустых заголовка. Контрольные суммы всех остальных полей
(accounts, transactions, current head и прочих) и всех блоков выше0 совпали до/после;
ни одной транзакции не удалено. Подробный отчёт: `evidence/public-pilot/genesis-repair.json`.
Это явная разовая процедура восстановления, не автоматический откат при запуске.

Проверка pinned Anvil1.7.1 также выявила, что `--transaction-block-keeper 1024`
удаляет старые транзакции при продвижении даже пустых блоков. Этот флаг убран из
постоянного стенда: потеря логов нарушила бы аудит старых голосований и историю сайта.
Ограничение кэша исторических **состояний** остаётся отдельным. История транзакций и
занимаемое ею место теперь растут с использованием; это не архив с постоянным размером.
Источник: [Anvil backend](https://github.com/foundry-rs/foundry/blob/v1.7.1/crates/anvil/src/eth/backend/mem/mod.rs#L2473-L2479).
