# Generic bundle CI → public certificate: agreed contract

2026-09-10. Transport and publication adapter is implemented and offline-tested in [CI REQUESTS.md](../../tools/lean-zk/ci/REQUESTS.md); a real generic request has not yet been dispatched. It reuses original RISC Zero3.0.6, existing immutable profiles and original Groth16/bridge verification. Source or guest semantics were not changed.

1. **Operator-owned submission.** The server uses its existing SSH authorization to create a child of its pinned trusted source commit, changing only `oncm-request.json`. Push `refs/heads/codex/proof-requests/<requestDigest>` in public `brodyga45/oncm`. Digest is SHA256 of exact JSON bytes including a server-job UUID nonce; retries preserve those bytes. Different owners have different nonces. CI verifies repository/head/parent, the single regular-file diff and exact committed digest. Only the operator chooses the trusted base; users cannot submit workflow or executable changes.

2. **Inline data.** Exact schema is `oncm-proof-request-v1`: requestNonce, profile (`perf05` or `v3`), exact profileId/imageId/goalHash, outcome0/1/2, source `{text,sha256}`, goal/export `{base64,sha256,bytes}`. Reject unknown/duplicate keys, noncanonical encodings, wrong hashes and sizes. Request≤4MiB; nonempty source≤512KiB; decoded export≤1MiB. Outcome0 requires only a well-formed goal. Outcomes1/2 require a full proof/refutation export beginning with the exact goal. Goal must end at structural Oncm.goal and begin with the immutable foundation. No user-selected paths, URLs, Lake scripts, prover options or binaries.

3. **Real checks and bounded compute.** The adapter checks data/foundation/boundaries, then the unchanged guest performs all mathematical and canonical binding checks inside original proving. There is no hidden theorem whitelist. Source is reviewed/reproducible metadata, not ZK-verified elaboration; this guest authenticates kernel artifacts. Original standalone CLI cannot execute-only, so the current adapter does **not** claim native/segment admission. The actual [Ix TN input](../../implementations/exchange/performance/ix-tn-add-zero-perf05/RESULTS.md) passed native and executor but used five proof segments; no ZK certificate exists for it. Runtime stays one heavy job, public4CPU, shared13GiB/no swap,1800s per case. Local expensive proving remains disabled. GitHub keeps only one pending run, so the server owns a durable queue/global remote lease and dispatches at most one. Cancellation is unsupported; UI detach is not remote cancellation.

4. **Original verification and separate publication.** Prover job is read-only. A separate trusted publisher validates compact data and exact request bindings, reruns original VerifyRequest, and receives only the job-scoped contents-write permission. It never executes artifact contents and strips the token from verifier subprocess environments. These follow GitHub's [job-specific token permissions](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token). It publishes `refs/heads/codex/proof-results/<requestDigest>` with `result.json`, plus receipt/certificate on success. Result format is `oncm-public-proof-result-v1`, status verified/failed, requestDigest/requestCommit/baseCommit/runId/attempt, input bindings, nested existing proof transport, compact resource counters and bounded error. It preserves the first verified result; later failed attempts cannot replace it. No force-push or log/token dump.

5. **Anonymous delivery and application acceptance.** Apps read result.json from the public raw branch URL; publisher also provides an immutable result-commit URL. This avoids the permissions and expiring redirect of the [Actions artifact download](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact). The app validates request/commit/base, canonical ABI and full journal, then calls its installed original immutable bridge. Repository identity and `verified:true` are not substitutes. Bind the accepted certificate to the current goal/profile/statement; a separate wallet action registers/resolves. Existing fixture-only UI importers still require explicit generic-bundle integration. Workflow/source publication, server activation and a real remote run remain subsequent reviewable steps; no paid service, dispatch or transaction occurred in this task.
