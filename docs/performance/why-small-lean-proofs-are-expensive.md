# Почему маленькая Lean-теорема даёт дорогой ZK-сертификат

2026-09-10. Уточнение пользователя: получить практически быстрый proving, исследуя существующие решения, а не только увеличивая таймауты. Текущий CPU CI — измерительный и бесплатный путь, не доказательство приемлемой задержки продукта.

## Что реально измерено

В [CI3](https://github.com/brodyga45/oncm/actions/runs/34416918326) получен настоящий Groth16 certificate: guest завершился за **13.10299 мс**, весь case с оригинальной проверкой receipt — за **465.69355 секунды** на четырёх CPU. Общий пик памяти **7,829,020,672 B / 7.291 GiB**, без OOM и swap, под общим пределом13GiB. Использовано1,796.24CPU seconds. Детали и артефакты — [журнал CI](../ci-proof-validation.md).

Это был даже не большой `Nat.add_comm`: использован минимальный профиль **perf05 с нулём аксиом**, `∀ P : Prop, P → P`, причём сертификат **outcome0 / registration** проверяет корректность постановки, ещё не её доказательство. Поэтому текущую задержку нельзя объяснять сложностью выбранной теоремы. Установленный v3 со стандартной арифметикой имеет дополнительную стоимость Lean export/kernel checking; его полный Groth16 pipeline этим прогоном не измерен.

Оригинальный фазовый журнал CI3 теперь разделяет затраты:

| Этап | Измеренный интервал UTC 9 сентября 2026 | Время |
|---|---|---:|
| Base STARK → начало lift | 23:27:28.979879 → 23:31:19.436185 | **230.456306 s** |
| Recursion lift | 23:31:19.436185 → 23:31:58.326573 | **38.890388 s** |
| identity_p254 → вызов Docker | 23:31:58.342505 → 23:34:40.703115 | **162.360610 s** |
| Docker Groth16 → parsing результата | 23:34:40.703115 → 23:35:13.656851 | **32.953736 s** |

Это интервалы между logging milestones, включающие небольшие переходные расходы; остаток до465.69s относится к остальной обвязке/проверке. Большая часть времени уходит на base STARK и identity_p254; сам Docker Groth16 занимает около7.1%. В исходном trace **524288 строк ×315 столбцов**, затем expanded domain ×4; recursion использует262144строки ×163столбца. Размеры и оригинальные исходники — в [разборе RISC Zero3.0.6](risc0-v3-cost-source.md).

Полученный receipt проверен оригинальным `Receipt::verify`, затем отдельно **оригинальным generic EVM verifier**: local chain31372, транзакция `0x7b42337d460b66f1a9fc944bed4fb91a1f8657ba8310ed335793667a649b7676`, **block120, status1, 251802gas**. Подменённые image и journal отклонены. CI `verified.json` и последующий `evm-verification.json` — разные свидетельства; сам CI не заявляет выполнения EVM-транзакции. Это успех регистрации perf05, **не theorem resolution**. Certificate имеет отдельные image/profile и **несовместим с установленными v3 application bridges**; проверка generic verifier не меняла registry или профиль приложений.

Исторический [CI2](https://github.com/brodyga45/oncm/actions/runs/34415338599) завершил guest за16.02ms, но не получил proof за600s на двух CPU:1,195.22CPU seconds, peak4.587GiB, нольOOM, до Docker не дошёл. Его переходы памяти не устанавливают точную фазу остановки. CI3 даёт измеренные времена собственного успешного прогона; приписывать их CI2 задним числом или объявлять контролируемым benchmark CPU2/CPU4 нельзя.

## За что платит универсальная zkVM

1. Lean elaboration разворачивает тактики в формальный proof term; экспорт сохраняет необходимые определения, типы и доказательства. Этот этап может выполняться обычным CPU.
2. Независимый NanoDa checker проверяет declarations, каноническую цель и policy. В выбранном подходе этот checker скомпилирован в RISC-V guest. RISC Zero должен доказать корректность **всего исполнения checker**, включая обработку данных, память и управление программой.
3. Prover строит trace и алгебраические ограничения виртуальной машины, выполняет расширение полиномов, commitments/Merkle hashing и FRI. Полином не является просто выражением `a+b-b-a`: он кодирует проверку машинного исполнения. Для FFT-подобных шагов характерна стоимость порядка `N log N`; ширина trace, расширение домена и дополнительные hash/field операции существенно увеличивают константу. Это не асимптотическая оценка всех шагов одним числом.
4. Затем выполняются рекурсивная компрессия/проверка доказательств и упаковка в Groth16 ради дешёвой Solidity-проверки. У этих стадий есть стоимость, слабо связанная с размером исходного Lean-текста. Повторять их отдельно для каждого крошечного запроса дорого.

Основание: [официальный RISC Zero proof-system paper](https://dev.risczero.com/proof-system-in-detail.pdf), [FRI/STARK explainer](https://github.com/risc0/risc0/blob/main/website/docs/proof-system/stark-by-hand.md), [pinned recursion implementation](https://github.com/risc0/risc0/blob/1cc70cf05033a79ebc90f07c679cb4bd1cd301b9/risc0/zkvm/src/host/recursion/prove/mod.rs). Старые опубликованные STARK benchmarks нельзя автоматически переносить на наш полный v3 Groth16 pipeline.

## Варианты, сохраняющие требуемый смысл

| Вариант | Что сохраняется | Что действительно меняется / ещё требуется |
|---|---|---|
| Готовый GPU prover Boundless, raw Groth16 | Тот же guest image, exact journal и оригинальная onchain cryptographic verification; prover не становится доверенным оракулом | Удалённое размещение computation, оплачиваемый request и его предел цены. Нужна проверка совместимости реального fulfillment с текущей версией и последующее EVM принятие; скорость нашей задачи пока не измерена |
| Boundless aggregated receipts / SetVerifier | Каждая claim остаётся криптографически доказанной; включение проверяется в наборе с доказанным корнем | Дорогой финальный proof/gas разделяется между запросами. Это прежде всего амортизация стоимости, не обещание меньшего latency одиночной заявки. Текущие мосты принимают raw Groth16: потребуется новый явный adapter/profile. Для независимых local chains нельзя просто довериться root из API — необходимо проверить root certificate или иной криптографически обоснованный путь |
| Специализированный prover для Lean kernel | Может сохранить проверку arbitrary Lean, если формальная семантика/kernel policy полны и соответствуют протоколу | Требуется готовая реализация и полный measured proof→EVM pipeline, а не только быстрый native check или параметры тестовой безопасности. Исследовательские проекты не подменяют эти критерии |
| Прямая onchain проверка formal proof term | Убирает генерацию zkVM execution proof и сохраняет недоверие к автору proof | Вычисление и размер доказательства переносятся в EVM/gas. Наличие готового полного Lean-compatible verifier и пригодность для больших proofs пока не установлены |

Для узкой арифметической DSL можно проверять существенно меньше ограничений, но это изменяет поддерживаемый язык. Нельзя объявить быстрый field circuit проверкой произвольного Lean `Prop` или молча отождествить натуральные числа с конечным полем. Подписи серверов/комитетов и optimistic challenge windows также меняют доверие или финальность и не считаются эквивалентной заменой текущего требования.

## Доступные сервисы: уточнение

[Bonsai прекращён с декабря 2025 года](https://docs.boundless.network/developers/tutorials/bonsai). Старые формы API keys и упоминания trial не являются действующим вариантом.

[Boundless](https://docs.boundless.network/developers/tutorials/request) документирует запросы, raw Groth16 и предел стоимости; [агрегированные receipts](https://docs.boundless.network/developers/tutorials/proof-types) используются по умолчанию. [GPU infrastructure](https://docs.boundless.network/provers/quick-start) — готовая открытая реализация, которую запускают провайдеры. Покупка proof и получение средств для неё не выполнялись. Актуальные доступность/цена/условия — в [remote-proving](../remote-proving.md).

Бесплатный CPU runner уже дал настоящий perf05 registration proof с успешной оригинальной EVM-проверкой. Измеренные465.69s и7.291GiB всё ещё не отвечают целям быстрого продукта и локального лимита2GiB. Доказательство/опровержение теоремы, resolution рынка и сертификаты для установленного v3 остаются отдельными проверками.
