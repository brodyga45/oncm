# Контекст и требования

Статус: исходная концепция принята со слов пользователя; механизмы реализации уточняются.

## Принято

- Проект начинаем с документации и детального проектирования архитектуры.
- Документация хранится в `docs/` и обновляется по ходу беседы.
- Пользователь задаёт общий замысел; ассистент участвует в обсуждении способов реализации, прорабатывает детали слоёв и контрактов.
- Документация может включать код, примеры и формальные контракты.
- Возможности финального продукта подробно описываем отдельно в [пользовательских сценариях](./user-scenarios.md). Принадлежность сценария к первой версии определяем отдельно по мере обсуждения.
- Сценарии для всех обсуждённых функций и ролей описываем как «айсберг»: что пользователь делает в вебе или SDK и что реально происходит за каждым шагом. Для LP предусматриваем описание обоих путей. Конкретные экраны/API до реализации помечаем как проектные предложения.

## Предстоит определить

- Детализация задач пользователей и критериев готовности продукта.
- Основные сценарии и границы первой версии.
- Термины предметной области.
- Функциональные требования и критерии ожидаемого поведения.
- Требования к нагрузке, задержкам, надёжности и данным, если они существенны для продукта.
- Внешние интеграции, среда исполнения и ограничения выбора технологий.

Этот список задаёт направления уточнения, а не дополнительные требования к продукту.

## Назначение продукта

Проект похож на prediction market, но предмет рынков — формализованные математические утверждения и производные утверждения о событиях протокола. Пользователь может создать рынок, предоставить ликвидность, торговать и предъявить доказательство для ончейн-резолва.

## Требования из исходного замысла

| ID | Принятое требование |
| --- | --- |
| R-001 | Любой человек может создать рынок на утверждение и добавить ликвидность. |
| R-002 | Торговля использует ончейн-AMM. Конкретная формула пока не выбрана. |
| R-003 | Базовое математическое утверждение задаётся кодом Lean. |
| R-004 | Доказавший утверждение оформляет доказательство на Lean, получает zk-сертификат и предъявляет его для ончейн-проверки и резолва. |
| R-005 | Каждый токен торгуется в T — основном токене проекта, соответствующем утверждению True. Токен доказанного утверждения превращается в T; токен опровергнутого становится False и ничего не стоит. Механизм и коэффициент превращения ещё не определены. |
| R-006 | Поддерживаются производные утверждения, например «проблема будет разрешена до timestamp» и «проблема разрешена в определённую сторону». Их резолв также проверяется ончейн. |
| R-007 | Governance может принимать новые символы и операции. |
| R-008 | Governance управляет пруферами, версиями Lean и широким кругом изменений протокола; принятие и исполнение решений должны быть ончейн. |
| R-009 | Предусмотрена группа выгодополучателей: адреса и их процентные доли комиссий. |
| R-010 | Любой может предложить перераспределение долей. Для применения требуется согласие всех и только тех, чья доля уменьшается. |
| R-011 | Максимально использовать готовые open source-решения; отдавать предпочтение признанным компонентам и стандартам. Предпочтительная реализация — соединение готовых частей с минимально необходимой собственной логикой. |
| R-012 | Явно разделить полностью ончейн-протокол и офчейн-часть: SDK, сайт и личный кабинет. |
| R-013 | Через приложение можно смотреть задачи и описания, оставлять комментарии, покупать токены, предоставлять ликвидность, запускать Lean и выполнять governance-действия. |
| R-014 | Пользователь входит своим кошельком; приложение предоставляет удобный интерфейс для действий над блокчейном. |

Пользователь предложил хэши исходников/Git как возможный способ идентификации версий. Конкретная схема идентификации и подтверждения сборки не выбрана.

Пользователь указал Gnosis как вероятный источник готовых токенов и AMM. Проверка подтвердила наличие Conditional Tokens и совместимых market maker-контрактов; это приоритетные кандидаты, а не уже выбранные зависимости. Сопоставление хранится в [готовых компонентах](./components.md).

Пользователь также предложил изучить Palomar и возможную интеграцию. Исследованы Comparator, Challenge/Solution, метаданные и каталог; выводы находятся в [Palomar и Comparator](./palomar-integration.md). Запрос на исследование не означает, что регистрация в Palomar обязательна для создания или резолва рынка. Новые сценарии помечены как предложения.

## Роли

Один адрес может совмещать несколько ролей: создатель рынка, поставщик ликвидности, трейдер, автор доказательства, отправитель zk-сертификата, участник governance, выгодополучатель, инициатор перераспределения долей.

Кто вправе участвовать в общем governance и что именно означает «пруфер» в его полномочиях, пока не определено. Автор доказательства и оператор вычислений для генерации zk-сертификата могут быть разными участниками — это предложение архитектуры.

## Граница «полностью ончейн»

Принятое уточнение пользователя: полностью ончейн-протокол отделён от офчейн-SDK, сайта и личного кабинета. Рынки, торговля, проверка оснований резолва, обязательное состояние и governance исполняются ончейн. Просмотр, описания, комментарии и инструменты запуска Lean находятся в слое приложения; через тот же интерфейс пользователь инициирует контрактные действия кошельком.

Подготовка доказательства и генерация сертификата относятся к вспомогательным вычислениям, точное место исполнения (браузер/локально/сервер) ещё не выбрано. Хранение полных формальных исходников и их доступность остаются открытыми вопросами. Подробности: [офчейн-приложение](./offchain-application.md).
