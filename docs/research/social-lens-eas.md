# Полный текст социальных данных ончейн: Lens V3 и EAS

Проверено 2026-09-10 чтением официальных исходников и npm metadata. Сборок, установки пакетов, развёртывания и транзакций в этом исследовании не было. **Для Vault рекомендован EAS + небольшой собственный `SchemaResolver`**: EAS уже хранит произвольные байты и авторство, а resolver добавляет правила профиля, дерева обсуждения, редакций и единственного текущего голоса. Это предложение реализации, не отчёт о готовой интеграции. Generic certificate import пока приостановлен; его код не менялся.

## Сравнение

| Требование | Lens V3 | EAS |
|---|---|---|
| Полный текст в текущем storage | `FeedCore.PostStorage.contentURI` — строка. Полный `data:` URI технически сохраняется целиком; обычная внешняя ссылка не делает её содержимое ончейн | `Attestation.data` — байты в `_db[uid]`. `abi.encode(string, …)` сохраняет сам текст |
| Профили / блог / ответы | Account metadata, Feed, `repliedPostId`, `rootPostId`, author и sequential IDs уже есть | Готовые attestations/schema/reference, но социальные типы и правила необходимо задать |
| Редактирование | Текущее `contentURI` перезаписывается, `PostEdited` содержит новую редакцию; полная история доступна через события, не через getter старых редакций | Новая attestation для каждой редакции; предыдущие полные записи остаются доступными через `getAttestation` |
| Голоса ±1, смена, снятие, запрет self-vote | В просмотренном `contracts/actions` есть tipping/collect; готовый контракт с нашими правилами голосов не найден | Собственный resolver проверяет и обновляет текущее значение; вся история голосов — attestations |
| Обычная независимая local EVM | Core написан на Solidity, но штатные compiler/deploy настройки ориентированы на zkSync. Прямой перенос всего deployment на Anvil не проверен | Обычные конструкторы `SchemaRegistry()` и `EAS(registry)`; адреса задаются локально. Готовые артефакты входят в npm пакет |
| Governance | AccessControl, rules, actions, proxies; это не готовое голосование Vault | Схемы неизменяемы; новая версия получает новый UID. Наш governance может принимать новую версию resolver/schema, не менять старые записи |

Основания Lens: [FeedCore: storage, создание, редактирование](https://github.com/lens-protocol/lens-v3/blob/4ad9ab574efc589ac0b90ea103d3aa465bb6368c/contracts/core/primitives/feed/FeedCore.sol), [Feed: author checks, events, getters](https://github.com/lens-protocol/lens-v3/blob/4ad9ab574efc589ac0b90ea103d3aa465bb6368c/contracts/core/primitives/feed/Feed.sol), [metadata storage](https://github.com/lens-protocol/lens-v3/blob/4ad9ab574efc589ac0b90ea103d3aa465bb6368c/contracts/core/base/MetadataBased.sol). Возможность `data:` URI — вывод из отсутствия проверки содержимого строки в этих методах, а не обещание совместимости с hosted Lens API.

## Что именно гарантирует EAS

В [Common.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/3683c3ec9383091eebd6f183e67b485e09a53dd7/contracts/Common.sol) `Attestation` содержит `attester`, `recipient`, `schema`, `refUID`, времена и `bytes data`. В [EAS.sol](https://github.com/ethereum-attestation-service/eas-contracts/blob/3683c3ec9383091eebd6f183e67b485e09a53dd7/contracts/EAS.sol#L436-L480) `_attest` копирует `request.data` и сохраняет структуру в `_db[uid]`; [getter](https://github.com/ethereum-attestation-service/eas-contracts/blob/3683c3ec9383091eebd6f183e67b485e09a53dd7/contracts/EAS.sol#L375-L383) возвращает запись. Редакции могут быть невозвратными отдельными записями. Revocation меняет время отзыва, не удаляет исходные байты.

При прямом `attest` автором становится `msg.sender`; у delegated path автор подтверждается штатной подписью. Нельзя просто завернуть вызов EAS в произвольный контракт и записать адрес пользователя в `data`: тогда `attester` будет адресом обёртки. Первый UI/SDK путь — кошелёк вызывает оригинальный EAS напрямую; relaying возможен позднее через официальный delegated API. [Авторство](https://github.com/ethereum-attestation-service/eas-contracts/blob/3683c3ec9383091eebd6f183e67b485e09a53dd7/contracts/EAS.sol#L94-L116).

EAS **не проверяет соответствие произвольных `data` строке schema** и не знает наши отношения «редакция», «ответ», «голос». Это обязанность resolver: canonical ABI decode, ограничения размера, автор/ссылки/версия/значение. Его callback доступен только EAS; `false` отклоняет всю attestation. Также `isAttestationValid(uid)` проверяет существование, поэтому нельзя использовать его как готовую проверку «активна, не отозвана, не истекла». [SchemaResolver](https://github.com/ethereum-attestation-service/eas-contracts/blob/3683c3ec9383091eebd6f183e67b485e09a53dd7/contracts/resolver/SchemaResolver.sol), [schema registry](https://github.com/ethereum-attestation-service/eas-contracts/blob/3683c3ec9383091eebd6f183e67b485e09a53dd7/contracts/SchemaRegistry.sol).

## Конкретный минимальный слой Vault

Три ABI schema с неизменяемым resolver, `expirationTime=0`, `revocable=false`. Поля ниже — проект наших schemas, не существующий стандарт EAS:

- **Profile:** `string displayName,string bio,bytes32 previousUID`. `recipient == attester`; `previousUID == latestProfile[attester]`; новый UID атомарно становится текущим. Адрес остаётся видимым независимо от имени.
- **Entry:** `uint8 kind,bytes32 statementId,bytes32 rootUID,bytes32 parentUID,bytes32 previousUID,string title,string body,bool deleted`. `kind` различает запись блога и комментарий. Первая запись создаёт стабильный root UID; редакция сохраняет автора, kind, context и parent, ссылается на текущую предыдущую редакцию. Ответ ссылается на стабильный root родителя того же контекста. Личный блог — записи `kind=blog` данного `attester`, не новый вид NFT.
- **Vote:** `bytes32 targetUID,bytes32 previousUID,int8 value`, где `value ∈ {-1,0,1}`; ноль снимает голос. Одна текущая запись на `(attester,targetRootUID)`, `previousUID` предотвращает конфликтующие обновления, запрещено голосовать за свой entry. Resolver изменяет `score[target]` на разность нового и старого значения; старые vote attestations остаются в истории. `refUID` указывает на target, история — через `previousUID`.

Resolver держит только указатели/current scores и проверяемые связи; полные тексты живут в оригинальном EAS. Публичные чтения через RPC + события восстанавливают профили, блог, дерево и историю после удаления локального кэша. Top/New используют onchain score и детерминированные tie-breakers по block/transaction/log order или явно сохранённой последовательности. Счёт голосов обсуждения не зависит от капитала, LP/BPT или governance веса. Социальная attestation подтверждает авторскую запись, **не истинность Lean-теоремы**; settlement остаётся в существующем ZK bridge.

Ограничения длины задаются в UTF-8 bytes в resolver и показываются в UI до подписи. Первые разумные пределы для проверки газом: name 80, bio 2048, comment 8192, blog body 16384 bytes. Это проектные пределы, не измеренные gas budgets. После edit/delete старая версия по-прежнему доступна в блокчейне; удаление оформляется tombstone новой редакцией.

Acceptance: восстановление полных текстов/всех редакций только из RPC; чужой edit и self-vote отклоняются контрактом; +1→−1→0 даёт score 1→−1→0; stale `previousUID` не создаёт fork; reply не переносится между statement/blog contexts; голос за редакцию нормализуется к стабильному root; UI смена кошелька не отправляет подготовленную запись прежнего автора. Deployment/additive integration не сбрасывает текущие chain/markets и не переписывает старые SIWE записи как будто это пользовательские транзакции.

## Точные компоненты и ограничения совместимости

- **EAS contracts npm 1.9.0**, [release gitHead `3683c3e…`](https://github.com/ethereum-attestation-service/eas-contracts/tree/3683c3ec9383091eebd6f183e67b485e09a53dd7), MIT; `EAS`/`SchemaRegistry` сообщают contract Semver **1.4.0**, это другая нумерация. Solidity **0.8.29**, OpenZeppelin **5.3.0**. [Package](https://github.com/ethereum-attestation-service/eas-contracts/blob/3683c3ec9383091eebd6f183e67b485e09a53dd7/package.json), [license](https://github.com/ethereum-attestation-service/eas-contracts/blob/3683c3ec9383091eebd6f183e67b485e09a53dd7/LICENSE). Прочитанные четыре основных файла совпали побайтно с current master `e6e9702…`; implementation следует pin release/package integrity, не moving master.
- **EAS SDK 2.10.0**, [commit `9ebc43f…`](https://github.com/ethereum-attestation-service/eas-sdk/tree/9ebc43fc0345679c8a521a1f497592015b9deb17), MIT, готовые `SchemaEncoder`, `EAS.attest`, `getAttestation`. SDK сам зависит от contracts **1.7.1**, ethers6/viem2: базовый ABI нужно подтвердить тестом с выбранным 1.9.0. Не подменять release контракт зависимостью SDK; при необходимости использовать официальный ABI 1.9.0 через уже имеющийся Vault viem, сохраняя готовый schema encoder. [Package](https://github.com/ethereum-attestation-service/eas-sdk/blob/9ebc43fc0345679c8a521a1f497592015b9deb17/package.json).
- **Lens V3**, [commit `4ad9ab5…`](https://github.com/lens-protocol/lens-v3/tree/4ad9ab574efc589ac0b90ea103d3aa465bb6368c), core Feed/Account **GPL-3.0-only**; отдельные base-файлы MIT. Зависимости включают OZ4.9, Solady, zkSync tooling; [Hardhat](https://github.com/lens-protocol/lens-v3/blob/4ad9ab574efc589ac0b90ea103d3aa465bb6368c/hardhat.config.ts) использует solc0.8.28/zksolc1.5.12 и zkSync networks, [штатный deploy](https://github.com/lens-protocol/lens-v3/blob/4ad9ab574efc589ac0b90ea103d3aa465bb6368c/deploy/deployImplementations.ts) устанавливает App/Account/Feed/Graph/Group/Namespace. Извлечение только Feed возможно как отдельная работа, но сейчас даёт больше интеграции без готовых нужных нам voting/history rules.

EAS экономит повторную реализацию хранения, UID, авторства, schemas, EIP-712/1271 и чтения. Он не является готовой социальной сетью; собственные schemas/resolver и UI остаются существенной, ограниченной частью работы. Если готовый Ethereum Comments Protocol закрывает те же требования меньшим объёмом кода, его можно одинаково использовать в нескольких приложениях — различие фреймворков не цель.
