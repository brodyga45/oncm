# Композиция сертификатов Lean-окружений

2026-09-10. Пользователь предложил переиспользовать готовые сертификаты математических библиотек через proof composition. Статус: архитектурное исследование и контракт кандидата; текущие v3/perf05 guest этого механизма **не реализуют**. Работающие независимые приложения и последовательный GitHub CI продолжаются без изменения их криптографических профилей.

## Подтверждённые готовые компоненты

- [RISC Zero 3.0 composition](https://dev.risczero.com/api/zkvm/composition): host `add_assumption(receipt)`, guest `env::verify(imageId, journal)`, затем разрешение assumptions при Succinct/Groth16 proving. Простое исполнение обычного verifier внутри универсальной VM не является этим оптимизированным механизмом.
- [Boundless Proof Composition](https://docs.boundless.network/developers/tutorials/proof-composition): доставка raw Groth16 и пример Echo → Identity. Это транспорт и криптографическая композиция программ, а не готовая семантика Lean-модулей.
- [Ix](https://github.com/argumentcomputer/ix): content-addressed Lean representation и цель сертификации библиотек. README формулирует возможность сертификата mathlib, но также помечает проект pre-alpha. В просмотренных материалах не найден опубликованный полный mathlib receipt, совместимый с нашим RISC Zero image/profile. Это отсутствие подтверждения, а не утверждение, что никто нигде не выпускал таких сертификатов.

Обычный Lean proof term и `.olean` cache не являются RISC Zero receipt. Они могут быть входами проверяемой программы, но не дают EVM криптографического подтверждения её исполнения. Совпадения названия mathlib недостаточно: важны версия, содержимое, зависимости, kernel semantics и политика аксиом.

## Где сейчас повторяется работа

### Реестр рынков как накапливаемая библиотека результатов

Уточнение пользователя: сохраняемые сертификаты доказанных утверждений должны формировать переиспользуемую базу для композиции. Это отдельная полезная функция продукта, а не только журнал окончательных цен/исходов.

Для каждого принятого результата сохраняются точные goal commitment и формальная декларация, profile/image/verifier identity, outcome, journal и proof bytes, происхождение принятия (chain/block/transaction), а в новом композиционном профиле также environment/dependency commitments. Proof bytes и формальные пакеты должны оставаться доступны в content-addressed offchain storage/экспортируемых пакетах; onchain состояние фиксирует принятую claim и нужные commitments. Одна ссылка на временный CI artifact с истечением срока хранения не обеспечивает долговременную доступность. Полные CI3 proof bytes уже сохранены в репозитории как начальное воспроизводимое свидетельство.

Позднее новая теорема использует подходящие удостоверенные результаты вместо повторного доказательства их корректности. Результаты совместимы только при согласованных формальных типах, окружении и kernel/axiom policy. Для NO переиспользуемым математическим результатом является доказанное `¬P`; отсутствие resolution или истечение срока само по себе не превращается в математическое доказательство `¬P`.

Текущие market certificates уже дают основу архива claims. Их автоматическое использование как импортируемых лемм ещё не реализовано: нужен проверяемый adapter между journal старого профиля и контекстом нового checker. Хранение сертификатов помогает последующей композиции, но не объявляет любой сохранённый certificate взаимозаменяемым с сертификатом библиотеки.

В `tools/lean-zk/checker/src/lib.rs` v3 проверяет committed goal prefix через `check_all_declars()`, а при resolution затем проверяет весь proof export, включающий этот prefix, снова через `check_all_declars()`. Это сознательно замыкает доверие к зависимостям внутри одного доказательства, но повторяет проверки. Внутри одного прогона можно исследовать корректное повторное использование уже проверенного состояния; между прогонами для этого нужны криптографически удостоверенные состояния.

Текущий journal `(domain, goalHash, profileId, outcome)` не задаёт общий контракт расширения Lean environment. Полученный outcome0 нельзя просто интерпретировать как универсальный сертификат mathlib или доказательство истинности цели. Новая семантика требует нового image/profile и явного governance admission, старые рынки сохраняют свои immutable профили.

## Контракт нового отношения

Предлагаемый guest доказывает переход корректного окружения E в корректное расширение E′. Конкретная сериализация/root construction ещё не выбрана и требует реализации с негативными тестами.

```text
EnvironmentClaim {
  domain: ONCM_LEAN_ENV_V1,
  kernelProfile,        // Lean-compatible checker, axiom/extension policy
  parentRoot,
  environmentRoot,
  declarationsDigest, // ordered additions / exact canonical encoding
  axiomSetDigest,
  schemaVersion
}

TheoremClaim {
  domain: ONCM_LEAN_THEOREM_V1,
  kernelProfile,
  environmentRoot,
  goalCommitment,
  outcome             // well-formed / proof / refutation, unambiguous
}
```

Инварианты отношения:

1. Base environment строится из явно фиксированных правил и аксиом. Его корректность либо доказана соответствующим root certificate, либо является точно описанной частью исходного verifier profile, а не сообщением сервера.
2. Сертификат импортируемого окружения проверяется по допустимому image/profile; его output root совпадает с используемым parentRoot. Заявленные, но не разрешённые assumptions не принимаются.
3. Тела определений, типы, параметры universes, inductive/constructor/recursor metadata, имена/идентификаторы и применимые flags аутентифицированы root. Сериализация исключает дублирование/подмену деклараций и неоднозначные ссылки.
4. Проверяются только новые declarations, но в точно этом окружении. Definition unfolding, definitional equality и чтение тел зависимостей могут всё ещё стоить заметно; сертификат не устраняет эти операции автоматически.
5. Расширение не меняет старые декларации и не добавляет неразрешённых аксиом/`sorryAx`. Граф зависимостей замкнут, отсутствуют неподтверждённые циклические допущения. Законные mutual declarations проверяются как целая группа.
6. Финальная claim связывает реальную цель рынка с environmentRoot, kernelProfile и исходом. NO доказывает отрицание конкретной цели, а не произвольный `False` в подменённом окружении.

Хеш окружения не заменяет доказательство корректности: он только связывает проверенную структуру с используемыми данными.

## Два варианта соединения сертификатов

### A. Рекурсивная композиция внутри proof system

Пользователь загружает receipt зависимостей. Host добавляет его как assumption, новый guest требует точный parent image/journal и проверяет расширение. Итоговое Succinct/Groth16 proof разрешает все зависимости. Контракт получает самодостаточное доказательство, пригодное для проверки на независимой цепочке. Не требуется вновь запускать checker на всех старых доказательствах, но composition/resolve и финальная компрессия имеют собственную цену.

Ниже схема, не исполняемая текущим guest:

```rust
// host: builder.add_assumption(parent_receipt);
// guest:
env::verify(approved_parent_image, &parent_claim_bytes)?;
let parent = authenticate_environment(parent_claim.environment_root, supplied_data)?;
let child = check_extension(parent, new_declarations, kernel_policy)?;
env::commit_slice(&encode_claim(child));
// prover: resolve all assumptions before producing accepted final receipt.
```

### B. Композиция через onchain registry проверенных окружений

Оригинальный verifier один раз удостоверяет environment certificate; контракт сохраняет `certified[kernelProfile][environmentRoot]`. Доказательство следующего шага утверждает **условное** отношение «из корректного E получается корректное E′», криптографически связывая входной root с использованными данными. Контракт принимает его лишь при уже сертифицированном E и подходящем transition verifier. После проверки сохраняет E′ или разрешает цель.

Это может убрать повторную рекурсивную проверку родительского receipt для каждого использования в одной цепочке. Доверенным сервером registry не становится: записи возникают только после проверки root/transition proofs. Требуются отдельные base/transition отношения, разделённые домены и проверенные contract preconditions. Для другой цепочки сертификационную цепочку нужно проверить заново или импортировать через криптографически обоснованный механизм; обычный API root неприемлем.

## Производительность и применимость

- Потенциально большой выигрыш: многие новые теоремы используют один и тот же большой dependency closure. Первичное вычисление сертификата библиотеки распределяется между ними.
- Не гарантируется ускорение нашего крошечного perf05 примера: в CI3 почти вся работа — доказательство небольшой VM execution и фиксированные recursion/Groth16 стадии. Родительское доказательство также требует composition work.
- Пакетирование новых theorem claims и общий финальный Groth16 — отдельная оптимизация, совместимая с переиспользованием environment certificates.
- Нельзя обещать стоимость пропорционально числу строк нового Lean-текста: короткая тактика может дать большой proof term, а короткий term — требовать дорогой reduction.

## Проверка перед внедрением

Следующий ограниченный прототип должен сертифицировать маленькое E, затем две независимые теоремы на нём; сравнить cold E+theorem с warm reuse. Измерять отдельно guest cycles, composition, финальное proof, peak RAM и EVM gas, сохраняя одинаковые mathematical/security policies. Обязательные отрицательные случаи: чужой parent root, изменённое определение, другое kernel profile, добавленная аксиома, неизвестная зависимость, неправильный outcome, неразрешённая assumption и неверная цель рынка.

Крупную mathlib-сертификацию и новые тяжёлые локальные сборки до этого не запускать. Для текущего smoke продолжается уже работающий GitHub pipeline; композиция не объявляется реализованной или измеренно быстрой по одному tutorial.
