# Утверждения и резолв

## Принятый замысел

Базовое утверждение — формализованная теорема в Lean. Кроме него существуют производные выражения, например пользовательское `will_bre_resolved_until(problem, timestamp)` и разрешение проблемы в определённую сторону. Governance может добавлять символы и операции.

Названия API ниже иллюстративные. Для читаемости первый оператор называем `ResolvedBy`; окончательное имя и семантика не согласованы.

## Предложение: два вида оснований

1. **Математическое основание:** проверяющая программа принимает доказательство конкретного `P` в зафиксированном окружении Lean, а ончейн-verifier проверяет zk-сертификат этого исполнения.
2. **Основание из состояния протокола:** детерминированное правило проверяет запись резолва, её исход и время. Такие правила могут исполняться непосредственно ончейн; дополнительный zk-сертификат нужен только если это продиктовано выбранной реализацией.

Пользователь хочет единый расширяемый язык. Разные способы проверки могут быть скрыты за общим интерфейсом выражений. Открыт вопрос: весь язык описывается в Lean или Lean используется для математических листьев, а композиция — через типизированное дерево выражений протокола.

## Идентичность Lean-утверждения

Предлагается привязывать утверждение к формальной цели, окружению импортов и политике допустимых оснований. Одинаковый текст в разных окружениях не следует автоматически считать одним утверждением: значение имён и нотации зависит от окружения. Lean отдельно отмечает различие между текстом, его elaboration и принятым ядром доказательством. [Lean: Validating a Proof](https://lean-lang.org/doc/reference/latest/ValidatingProofs/).

Актуальный кандидат представления: commitment к каноническому `Prop`, корень окружения постановки, версия формата и политика проверки. Snapshot исходников и имя объявления сопровождают цель отдельным манифестом; будущий Solution не входит в её исходную идентичность. Раннее предложение включать хэш исходного Challenge в основную спецификацию уточнено: само это поле не доказывает source→goal. Выбор авторитетного kernel artifact либо доказанной elaboration исходников раскрыт в [системе доказательств](./proof-system.md) и [исследовании](./research/proofs.md).

Не требуется автоматически отождествлять математически эквивалентные формулировки. Канонизация и запрет дубликатов пока не выбраны. При создании публикуется цель без готового доказательства; незаполненное доказательство нельзя принимать как основание резолва.

Предложение по примеру Palomar — публиковать краткий Challenge отдельно от Solution и метаданных. Comparator — готовый кандидат проверки их соответствия. Внешний Palomar ID, название результата и текст аннотации не заменяют формальную идентичность. См. [исследование](./palomar-integration.md).

## Состояние знания и логическое отрицание

Предлагаемая модель, пока не принята:

```text
Unresolved -- принято доказательство P --> ProvenTrue
Unresolved -- принято доказательство ¬P --> ProvenFalse
```

Пользователь подтвердил результат для доказанного и опровергнутого утверждения: его токен превращается соответственно в T или в ничего не стоящий False. Предлагаемое основание опровержения базового математического P — доказательство `¬P`; точный формат такого сертификата ещё не согласован. Наличие отдельного торгуемого токена `¬P` из этого не следует.

`Unresolved` не означает `False`. Отсутствие найденного доказательства не доказывает отрицание; базовый рынок может оставаться неразрешённым неопределённо долго. Экономические последствия описываем отдельно.

Если когда-либо проходят сертификаты и для `P`, и для `¬P`, это конфликт оснований системы, а не обычная смена мнения рынка. Политика остановки, диагностики и судьба уже исполненных расчётов ещё не выбрана. Правило «первый сертификат навсегда прав» не считается согласованным.

## Предлагаемая семантика ResolvedBy

`ResolvedBy(problemId, deadline)` означает: «протокол принял разрешение указанной проблемы в любую из разрешённых сторон в блоке с временем не позже `deadline`».

Пусть `resolvedAt` — сохранённое контрактом время первого принятого резолва, а `now` — время текущего блока. Отсутствие резолва представляется отдельным состоянием.

| Условие | Результат производного выражения |
| --- | --- |
| Есть принятый резолв и `resolvedAt <= deadline` | True |
| `now > deadline` и нет принятого резолва с `resolvedAt <= deadline` | False |
| Дедлайн ещё не прошёл и своевременного резолва пока нет | Unresolved |

Это предложение с включительной границей `<=`. Строгое «до» (`<`) — альтернативная семантика, которую нужно выбрать явно.

Пример: сертификат создан до дедлайна, но принят транзакцией после него — базовое утверждение может разрешиться, а `ResolvedBy` получает False. Время написания доказательства и отправки транзакции не используется в предложенной модели.

В EVM доступен `block.timestamp` в секундах Unix; конкретная сеть пока не выбрана. Это время блока по правилам сети. [Solidity: Block and Transaction Properties](https://docs.soliditylang.org/en/latest/units-and-global-variables.html#block-and-transaction-properties).

Само наступление времени не записывает результат в контракт: для изменения состояния нужен вызов транзакцией либо отдельная возможность целевой сети. Предложение — permissionless-вызов `resolveDerived`, который может быть частью другой операции. Кто оплачивает и стимулирует такие вызовы, пока не определено.

Отрицательный исход после дедлайна опирается на полноту собственного реестра принятых резолвов, а не на поиск доказательств во внешнем мире. Реорганизации и финальность наследуются от выбранной сети. Сохранение исторического резолва требуется даже если производное выражение вычисляется значительно позже дедлайна.

## Производные по стороне и другие операции

Кандидаты для обсуждения:

- `ResolvedAs(problemId, outcome)` — принят резолв конкретной стороны.
- `ResolvedAsBy(problemId, outcome, deadline)` — принят указанный исход к дедлайну.
- Логические операции над утверждениями — возможное расширение, пользователем конкретно не перечислены.

Для `ResolvedAs` нужно выбрать: это меняющийся запрос «сейчас уже разрешено» или рынок на будущее событие. Нельзя финально присваивать False будущему событию только потому, что оно пока не наступило.

Для каждой новой операции governance должен принимать её типы аргументов, версию, способ проверки, поведение при неизвестных входах и правила окончательности. Это предлагаемая структура расширения, а не уже выбранный механизм governance.

Актуальная рекомендация для `ResolvedAs` — событие будущего финального исхода: True при выбранной стороне, False при противоположной, Unresolved до записи. Для `ResolvedAsBy` добавляется срок. Для derived над derived берём время фактической записи, без заднего числа. Полная таблица, ограничения DAG и permissionless bounded batch: [сборка операторов](./integration-blueprint.md).
